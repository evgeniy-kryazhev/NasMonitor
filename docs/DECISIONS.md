# Решения desktop spike

## 2026-10-17 — заполнение томов через Информационный центр

Пользователь запросил чтение storage без administrators после DSM 105 у
SYNO.Storage.CGI.Storage load_info. Документация Synology определяет 105 как
общий отказ сессии в разрешении, а не идентификатор конкретной роли. Роль
«Мониторинг системы» включает Info Center > General, Network, Storage.
Публичной гарантии разрешений каждого внутреннего API документация не даёт.

Основным источником томов делаем обнаруженный SYNO.Core.System v1 info
с type=storage: vol_info[].name, used_size, total_size (байты). Этот формат
используется существующими клиентами DSM, включая Homarr. В отличие от
File Station он не требует разрешения на файловые приложения/общие папки и
описывает заполнение тома, а не пользовательскую квоту. Используем ту же
обнаруженную SystemUri, SID и X-SYNO-TOKEN. Запрос раз в 60 секунд, ручной
refresh обновляет сразу; дополнительных сессий/опросов на виджет не создаём.

Сначала проверяем, что ответ даёт валидный полный набор томов. При отсутствии
данных/отказе пробуем прежний Storage Manager load_info как совместимый резерв.
При успехе основного источника не вызываем Storage Manager. Списки из разных
источников не объединяем, некорректные тома не пропускаем в проценте, отсутствие
данных не превращаем в ноль. Ошибки истечения сессии и отмену не скрываем
резервным запросом. Сохраняем наиболее полезную причину при отказе обоих путей.

Рассматривались Core.Storage.Volume, storage_v2 и SNMP: это отдельные API/форматы
или настройка NAS; для этого среза достаточно проверяемого type=storage.
Implemented/Automated-tested проверяются на синтетических ответах. Работа с
делегированной ролью конкретного NAS остаётся Unverified до ручного запуска.

Источники:
- [Synology: делегированные роли](https://kb.synology.com/en-br/DSM/help/DSM/AdminCenter/file_user_delegate?version=7)
- [Synology: общий код 105](https://kb.synology.com/en-us/DG/DSM_Login_Web_API_Guide/2)
- [Homarr: запрос storage и поля vol_info](https://github.com/homarr-labs/homarr/blob/dev/packages/integrations/src/synology/synology-client.ts)

## 2026-10-17 — диагностика недоступного заполнения тома

Пользователь подтвердил CPU/RAM/сеть/температуру/uptime после CSRF-исправления,
но хранилище осталось «—»; tooltip в предпросмотре не появился. Разбор volumes
уже допускает один том без storagePools. Не добавляем предположительные форматы
ответа и не запрашиваем административные права без фактической причины отказа.

Сохраняем только числовой DSM-код ошибки группы в NasMetric и показываем его
в StorageDetail. При частичной работе с недоступным хранилищем MonitorDetail
(существующая видимая строка настроек) показывает причину хранилища вместо
общей подсказки. Сырые ответы, идентификаторы сессий и секреты в диагностику
не передаются. Остальные показатели и polling продолжают работать независимо.
Альтернатива — требовать tooltip/дамп HTTP — недостаточна для пользователя и
не нужна для первичного различения denied/unsupported/invalid/unavailable.
Тестируем прямой и вложенный ответ с одним томом без пула, перенос кода 105
и текст видимой причины. Реальная причина отсутствия storage пока Unverified.

## 2026-10-17 — CSRF-токен в заголовке POST-запроса DSM

После исправления session пользователь подтвердил успешный вход, но мониторинг
показал «Сессия истекла или была прервана». Проверка транспорта выявила передачу
SynoToken только в form body. В официальной документации Synology для CSRF
указан query string или заголовок X-SYNO-TOKEN. Переносим токен в заголовок
конкретного HttpRequestMessage; SID, пароль и OTP остаются в POST body.
Не используем DefaultRequestHeaders, чтобы HttpClient не сохранял токен между
независимыми входами. Общий CookieContainer не включаем, URL не содержит секретов.
CSRF-защиту на NAS не отключаем. Альтернатива с токеном в URL отклонена из-за
риска записи query в proxy/access logs. Общий транспорт исправляет discovery
после входа, метрики и logout как для probe, так и для мониторинга.

Тест с CSRF-проверкой воспроизводит 119 на старом коде. Это проверка модели
сервера; устранение реальной ошибки на NAS остаётся Unverified до повторного
подключения. Не связываем эту ошибку с необходимостью прав administrators.

Источник: [Synology DSM Developer Guide — CSRF](https://global.download.synology.com/download/Document/Software/DeveloperGuide/Firmware/DSM/6.0/enu/DSM_Developer_Guide_6_0.pdf).

## 2026-10-17 — авторизация без произвольного имени DSM-приложения

Пользователь сообщил DSM 402 при разрешённом доступе к DSM и показал
делегированную роль «Мониторинг системы». Проверка кода обнаружила, что probe
передаёт `session=NASMonitorProbe`, а мониторинг — `session=NASMonitor`.
Эти имена не зарегистрированы как приложения DSM. Параметр session в Auth v6
не является локальной меткой нашего клиента: документация описывает его как
необязательное имя сессии для приложений DSM.

Убираем session из login/logout обоих путей. Следуем официальному примеру
общего входа DSM; logout адресуется только полученным `_sid` и SynoToken.
Каждый вход по-прежнему получает собственный SID; независимость сессий
на реальном NAS, включая влияние probe на активный мониторинг, требует проверки.
Альтернативы: имя DSM оставляет лишнее предположение о серверной политике;
FileStation требует ненужного доступа к файловому приложению; повышение до
administrators не исправляет некорректное предположение клиента.

Регрессионные тесты проверяют оба запроса и адресный logout. Устранение 402
и доступность каждого Core/Storage API с делегированными правами — Unverified
до повторного подключения пользователя. Не считать вход доказательством доступа
ко всем метрикам и не требовать administrators на основании одного кода 402.

Источник: [DSM Login Web API Guide, Login и Logout](https://global.download.synology.com/download/Document/Software/DeveloperGuide/Os/DSM/All/enu/DSM_Login_Web_API_Guide_enu.pdf).

## 2026-10-17 — обновления из GitHub Releases

Источник — публичные stable releases evgeniy-kryazhev/NasMonitor, определённый
по origin репозитория. Проверяем latest при запуске и раз в 6 часов; prerelease,
draft, downgrade и неподходящий RID не устанавливаем. Установка инициируется
кнопкой пользователя после сообщения о новой версии. В smoke нет GitHub-запросов.

Сохраняем self-contained single-file delivery: используем отдельные assets
NasMonitor-win-x64.exe, NasMonitor-osx-arm64 и NasMonitor-osx-x64. SHA-256 берём
из digest GitHub API либо SHA256SUMS.txt того же релиза. Непроверенный файл не
запускается. Контрольная сумма защищает целостность; доверие к издателю остаётся
на HTTPS и доступе к GitHub-репозиторию, это не замена code signing.

Текущий executable копируется как helper в staging-каталог. Helper без Avalonia
ждёт завершения исходного процесса, повторно проверяет checksum и заменяет файл
через соседний temporary/backup с восстановлением при ошибке. Никаких shell-команд,
передачи паролей или повышения привилегий. Для macOS сохраняются executable modes;
обновляется bundled executable, существующие данные и настройки не затрагиваются.
Ошибки установки записываются контролируемым кодом и показываются при следующем
старте. Необходим доступ записи к каталогу приложения. Debug/dotnet-host запуск
не обновляется. macOS и реальная установка опубликованного релиза — Unverified.

Velopack/Sparkle рассматривались как альтернатива: требуют изменения текущего
формата доставки/платформенной упаковки. Для существующего portable формата
оставляем отдельный тестируемый механизм замены executable.

## 2026-10-17 — несколько независимых виджетов

WidgetWorkspace владеет коллекцией экземпляров: у каждого свой ID, ViewModel,
controller, окно, геометрия, внешний вид и NAS. Manager редактирует выбранный
экземпляр; обновления других окон не перезаписывают его форму. Общий presenter
подписывает экземпляры на единственный NasMonitoringCoordinator, поэтому два
виджета одного NAS не создают дополнительных сессий и polling loops.

Версионированный widgets.json хранит состав и выбранный экземпляр. Первый
legacy-виджет получает новый ID с признаком прежнего каталога настроек;
существующие layout/appearance/source.json читаются без потери данных.
Новые экземпляры используют widgets/<id>/. Удаление меняет каталог и закрывает
только соответствующее окно; не удаляет NAS, пароль или общий мониторинг.
Оставляем минимум один виджет. Новые виджеты требуют явного выбора NAS.
Неприменённый черновик внешности сохраняется при переключении между виджетами.

Альтернатива — отдельный presenter/coordinator на каждое окно — отвергнута
из-за дублирования опросов. Общий арбитр жеста допускает перетаскивание только
одного окна одновременно. Native hosts остаются отдельными платформенными
реализациями; macOS и реальный DSM всё ещё требуют ручной проверки.

## 2026-10-17 — растягиваемая рабочая область

Уточнение пользователя: полоса прокрутки должна находиться у правой границы
самого окна, а не у границы формы с внешним отступом 28 DIP. Правая граница
ScrollViewer совпадает с границей страницы. По итоговому уточнению пользователя
внутренние отступы возвращены: заголовок и содержимое обеих вкладок имеют
одинаковый правый отступ 28 DIP, а сама прокрутка не имеет внешнего отступа.
Smoke отдельно проверяет край окна и совпадение границ формы/заголовка.

Пользователь попросил привязать рабочую область к границам окна. Убираем
программные ограничения ширины страниц 1000/840 DIP и левое выравнивание контейнеров.
Grid растягивается по доступной ширине/высоте, строка вкладок занимает остаток
высоты. ScrollViewer каждой вкладки доходит до нижнего края; нижний отступ
содержимого находится внутри прокрутки. Колонки формы/preview пропорциональны
с минимальной шириной для читаемости. DSM-форма также растягивается, её нижняя
кнопка остаётся в отдельной фиксированной строке.

## 2026-10-17 — ручная высота с минимумом по содержимому

Пользователь уточнил: нужна свободная ручная высота, а содержимое задаёт только
нижнюю границу. Прежняя автовысота ошибочно заменяла размер при каждом resize.
Теперь сохраняем max(запрошенная высота, измеренная высота содержимого).
Высоту можно увеличивать, уменьшать до этого минимума и сохранять. Отдельный
переключатель AutoHeight убран; старое JSON-поле игнорируется при чтении.
Предпросмотр по-прежнему имеет естественную высоту. При добавлении блоков окно
вырастает, если нужно; скрытие блоков позволяет уменьшить его вручную.

## 2026-10-17 — высота карточки по содержимому

По уточнению пользователя предпросмотр получает естественную высоту Avalonia
без фиксированного Height/MinHeight. Desktop widget измеряет тот же visual tree
при текущей ширине и применяет вычисленную высоту через существующий native host.
AutoHeight включён по умолчанию, включая старый JSON без этого поля. При отключении
можно задать высоту вручную. У скрытых групп нет пустых рядов. После изменения
содержимого высота ограничивается рабочей областью монитора; если всё не помещается,
остаётся ScrollViewer. Ширина и положение продолжают задаваться пользователем.
Не используем native SizeToContent после WorkerW reparent: измерение Avalonia
отделено от native размещения, чтобы сохранить DPI и desktop-привязку.

## 2026-10-17 — реальные CPU/RAM и общий мониторинг DSM

Пользователь подтвердил исправленный интерфейс и поручил заменить DEMO реальными
метриками. Добавляем нормализованные nullable CPU/RAM и один polling-loop на NAS
в Infrastructure, с независимыми состояниями, ограниченной конкуренцией, отменой,
backoff и закрытием сессии. Общий DSM protocol используется проверкой и постоянной
сессией, чтобы не дублировать правила TLS, discovery paths и ошибок авторизации.
Каждый виджет только читает общий кэш; выбранный NAS сохраняется отдельным ID.
Без выбранного NAS показываем пустое состояние; synthetic данные только в smoke.

Опрос по умолчанию каждые 10 секунд. Автозапуск — для включённых профилей с паролем
в OS store. Ручное подключение сохранённого профиля допускает пароль/OTP без
сохранения; после входа держим только SID/CSRF. Истечение сессии допускает повторный
вход из OS store; ошибки пароля/2FA останавливают автоматические попытки до
явного действия пользователя. Основной/внешний endpoint выбирается явно;
внешний выбор действует до перезапуска, автозапуск использует основной.

Метрики читаются через обнаруженный SYNO.Core.System.Utilization v1, method=get:
CPU = user_load + system_load + other_load, RAM = memory.real_usage.
Этот Core API не имеет публичной гарантии совместимости Synology; версия/поля
проверяются, unsupported/denied/missing не заменяются нулём. Альтернатива SNMP
потребовала бы отдельной настройки NAS и credentials; не вводим её скрытно.
По дополнительному скриншоту пользователя storage/network/temperature/uptime
также входят в текущий срез; несколько desktop-окон остаются дальнейшим этапом V1.
Сеть берём из total.rx/tx (bytes/sec), температуру/uptime/model из Core.System info,
тома из Storage.CGI.Storage load_info. Системные/дисковые данные запрашиваем
раз в 60 секунд, храним их собственные timestamps и отмечаем отказ отдельно.
Агрегат хранилища — сумма использованных байт / сумма ёмкостей логических томов.

Источники протокола и формата:
- https://global.download.synology.com/download/Document/Software/DeveloperGuide/Os/DSM/All/enu/DSM_Login_Web_API_Guide_enu.pdf
- https://github.com/mib1185/py-synologydsm-api/blob/master/src/synology_dsm/api/core/utilization.py

формы живёт при переключении; отдельное окно DSM не создаём. Пароль/OTP

## 2026-10-17 — переход к подключению DSM по решению пользователя

Пользователь подтвердил resize на своей Windows и явно отложил проверки macOS,
поручив продолжить Synology DSM. Это разрешение перехода к этапу подключения;
macOS и оставшиеся lifecycle-кейсы сохраняют статус Unverified.

Добавляем Core-контракты профиля/результата/secret store, Providers.Synology
(discovery, проверка транспорта, login/logout, capabilities), Infrastructure
(версионированный JSON профилей), отдельное окно подключения в App. Секреты
опционально сохраняются Windows Credential Manager / macOS Keychain через
платформенные adapters. В JSON только opaque reference; OTP и SID не сохраняем.

HTTPS обязателен для авторизации первого среза, TLS без исключений. HTTP без TLS
и автоматический переход на внешний адрес отложены: не отправляем пароль на
другой endpoint после ошибки. Endpoint выбирает пользователь, редиректы запрещены.
API paths берём из discovery, проверяем относительный путь в /webapi/ и same origin.
Auth используем версии 6 (пересечение поддерживаемых версий), POST form, sid+CSRF.
Проверка создаёт временную сессию и выполняет logout в finally с отдельным timeout.
Capabilities означают только объявленные API, не доказательство прав на метрики.
Polling и отображение реальных метрик — следующий срез; DEMO не выдаём за DSM.

## 2026-10-17 — перемещение указателем в edit-режиме

Добавляем Avalonia pointer capture, экранный якорь на начало жеста и перемещение
через существующий desktop host. BeginMoveDrag не используем: Windows-виджет
остаётся дочерним HWND WorkerW. Attach при движении не меняет parent, если он
уже правильный; SetWindowPos сохраняет Z-order и не активирует окно. На macOS
Avalonia задаёт Position, AppKit host сохраняет desktop level. Окно не скрываем
на каждом движении. На отпускании/потере capture сохраняем последнюю позицию.
Manager включает edit одной кнопкой; locked запрещает начало жеста.
Shell input, DPI и перенос между мониторами требуют ручной проверки на обеих ОС.
Размер пока меняется только через Manager.

WorkerW под SHELLDLL_DefView может не получать pointer events. Windows host
дополнительно предоставляет опрос GetCursorPos/GetAsyncKeyState в edit-режиме.
Начало жеста разрешено только в прямоугольнике виджета, когда WindowFromPoint
указывает на сам виджет или desktop shell; AccessibleObjectFromPoint исключает
иконки ListView. Другие окна не запускают жест. Глобальные hooks не нужны.
При отказе accessibility начало жеста на перекрывающем shell запрещено.

## 2026-10-17 — границы и платформенные механизмы

Создаём App (Avalonia + UI + lifecycle), Hosting (контракт без Avalonia),
Platform.Windows и Platform.MacOS (узкие native adapters), Core (геометрия,
синтетические метрики), Core.Tests. Провайдер DSM пока не создаём.

Windows: экспериментальный WorkerW Explorer, WS_CHILD + SetParent, NOACTIVATE.
Это недокументированный shell protocol, а не гарантия совместимости.
При недоступном WorkerW виджет скрывается, Manager показывает отказ.
Проверка host выполняется периодически; потеря HWND требует пересоздания окна.
Альтернатива обычного окна с Topmost=false отвергнута: нарушает ТЗ.

macOS: публичные Objective-C/AppKit API, CGWindowLevelForKey(desktopWindow)+1,
canJoinAllSpaces + stationary + ignoresCycle, ignoresMouseEvents в locked.
Нативный NSWindow получается из NSView.window, если Avalonia возвращает NSView.
Приватные API и таймер принудительного orderBack обычного окна не используются.
Manager остаётся доступен в Dock для диагностики и завершения spike.

Редактирование: Manager задаёт абсолютные физические X/Y и размер в DIP.
На Windows reparented child нельзя надёжно двигать обычным window drag;
поэтому перемещение/resize доступны через Manager на обеих ОС. Это сознательное
ограничение spike; pointer drag/resize требует отдельного исследования.
Настройки сохраняются атомарно; при пропавшем дисплее геометрия возвращается
в рабочую область основного. Проверки после сна и смены дисплеев выполняются
тем же периодическим lifecycle monitor. Один synthetic publisher для всех views.

Источники:
- https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setparent
- https://docs.avaloniaui.net/docs/app-development/native-interop
- https://developer.apple.com/documentation/coregraphics/cgwindowlevelkey/desktopwindow
- https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct

Native API success означает только принятие вызовов. Все OS acceptance кейсы
остаются Unverified до проверки пользователем; следующий этап заблокирован ими.

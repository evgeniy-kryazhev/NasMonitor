# Desktop Widgets: механизмы, риски и протокол испытаний

## Контракт поведения
- За обычными окнами; не always-on-top.
- Видимы при раскрытом рабочем столе.
- Не дублируются в taskbar/Dock, если это возможно.
- Работают на нескольких мониторах; сохраняют размер/координаты.
- Переход в режим редактирования для drag/resize/lock, если взаимодействие с desktop shell позволяет это.

## Windows
Проверить Win32-handle Avalonia-окна и реальную привязку к desktop layer Explorer. `Progman` / `WorkerW` и `SetParent` нередко используются, но это не документированный официальный API стабильных виджетов. Особое внимание иконкам рабочего стола, входным событиям, virtual desktops, Win+D, shell restart и DPI. Не записывать 'готово' по одному успешному тесту.

## macOS
Использовать AppKit `NSWindow` level и collection behavior в разрешённых API. Проверять Finder desktop, Mission Control, Spaces, Stage Manager, fullscreen apps и многодисплейный режим. Уровень под обычными окнами сам по себе не доказывает корректное поведение системного виджета. Не использовать приватные Apple API.

## Рекомендуемый испытательный план
1. Прототип Avalonia-окна с тестовыми CPU/RAM.
2. Несколько стандартных окон над виджетом.
3. Клик по виджету: не поднимать его над приложениями.
4. Win+D/Show Desktop; вернуть приложения.
5. Explorer/Finder restart (там, где тест допустим) и восстановление.
6. Изменение DPI/масштаба, смена разрешения, отключение второго дисплея.
7. Сон/пробуждение, новый вход в систему.
8. macOS: Mission Control, Spaces, fullscreen, Stage Manager.
9. Windows: virtual desktops, переключение окон и иконки рабочего стола.
10. Записать результат каждого испытания для каждой ОС и версии.

## Failure policy
Если desktop-host mechanism не сработал: зафиксировать диагностический статус, не выдавать обычное окно за полноценное решение. Обсудить дальнейший способ обеспечения desktop mode; временное окно разрешается лишь как диагностический fallback, не как принятая V1.
